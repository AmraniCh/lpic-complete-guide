# 110.3 Securing data with encryption

**Weight: 4**

The candidate should be able to use public key techniques to secure data and communication.

**Objectives**

- Perform basic OpenSSH 2 client configuration and usage.
- Understand the role of OpenSSH 2 server host keys.
- Perform basic GnuPG configuration, usage and revocation.
- Use GPG to encrypt, decrypt, sign and verify files.
- Understand SSH port tunnels (including X11 tunnels).

**Terms**

`ssh`, `ssh-keygen`, `ssh-agent`, `ssh-add`, `~/.ssh/id_rsa` and `id_rsa.pub`, `~/.ssh/id_dsa`, `~/.ssh/id_ecdsa`, `~/.ssh/id_ed25519` (and their `.pub`), `/etc/ssh/ssh_host_rsa_key` and `ssh_host_rsa_key.pub`, `/etc/ssh/ssh_host_dsa_key`, `/etc/ssh/ssh_host_ecdsa_key`, `/etc/ssh/ssh_host_ed25519_key`, `~/.ssh/authorized_keys`, `ssh_known_hosts`, `gpg`, `gpg-agent`, `~/.gnupg/`

### Key pairs

Traditional (symmetric) cryptography uses one shared password to both encrypt and decrypt, which means the password has to be shared safely. **Public key** (asymmetric) cryptography instead uses a pair of keys generated together: a **private key** you keep secret and a **public key** you give to anyone. Whatever one key encrypts, only the other can decrypt.

So people encrypt a message with your public key and only you, holding the private key, can open it, even if the encrypted message travels over an open network. Both SSH and GnuPG are built on this idea.

### SSH host keys

SSH uses key pairs to authenticate hosts and encrypt traffic. Each server has **host keys** in `/etc/ssh/`, one pair per algorithm: `ssh_host_rsa_key` / `ssh_host_rsa_key.pub`, and the same for `ssh_host_dsa_key`, `ssh_host_ecdsa_key`, and `ssh_host_ed25519_key`. On the first connection the client shows the server's fingerprint and asks you to trust it:

```
$ ssh 192.168.70.2
The authenticity of host '192.168.70.2' can't be established.
ED25519 key fingerprint is SHA256:4Wp2zz6sgPAhnbqhkNjOd6QDpNQ4jvjX7qAzslPX09U.
Are you sure you want to continue connecting (yes/no)? yes
```

The server's public key is then saved in your `~/.ssh/known_hosts` (a system-wide list can live in `ssh_known_hosts`). If that key later changes, SSH refuses to connect and warns loudly, because it may mean someone is impersonating the server:

```
@@@ WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED! @@@
Someone could be eavesdropping on you right now (man-in-the-middle attack)!
```

Once you are sure it is legitimate (for example the server was reinstalled), remove the stale entry with `ssh-keygen`:

```
$ ssh-keygen -R 192.168.70.2
```

### Creating your own key pair

`ssh-keygen` makes a personal key pair. The `-t` switch chooses the algorithm: `rsa` (the default), `dsa`, `ecdsa`, or `ed25519`:

```
$ ssh-keygen -t ed25519
Enter file in which to save the key (/home/jadi/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
Your identification has been saved in /home/jadi/.ssh/id_ed25519
Your public key has been saved in /home/jadi/.ssh/id_ed25519.pub
```

This writes the private key `~/.ssh/id_ed25519` and the public key `~/.ssh/id_ed25519.pub` (with `rsa` you get `~/.ssh/id_rsa` and `~/.ssh/id_rsa.pub`). Protect the private key with a passphrase; if you set one, you are asked for it each time the key is used.

### Key-based (password-less) login

Instead of a password, the server can authenticate you by your key: put your **public** key in the server account's `~/.ssh/authorized_keys`, and make sure `PubkeyAuthentication yes` is in the server's `/etc/ssh/sshd_config`. Then your client proves your identity with the private key and you log in with no password. This is safer and easy to automate: to grant someone access you only need their public key, never a shared password. Copy it with `ssh-copy-id` rather than editing the file by hand:

```
$ ssh-copy-id 192.168.70.2
Number of key(s) added: 1
```

### ssh-agent and ssh-add

`ssh-agent` is a key manager that holds your unlocked private keys in memory, so a passphrase-protected key is only entered once. Start it and load keys with `ssh-add`:

```
$ eval $(ssh-agent)
$ ssh-add
Identity added: /home/jadi/.ssh/id_rsa (jadi@debian)
$ ssh-add -l          # list loaded keys
```

The agent can also forward your keys safely in memory, so from server A you can use them to reach server B without ever copying the private key onto A.

### SSH tunnels

SSH can carry other traffic inside its encrypted connection.

**Local forwarding** (`-L`) sends a local port through the SSH server to somewhere else:

```
$ ssh -L 9000:hckrnews.com:80 root@5.161.197.79
```

Now `localhost:9000` on your machine reaches `hckrnews.com:80` through that server. This is how you reach a service that only listens locally on the remote host.

**Remote forwarding** (`-R`) does the reverse, exposing a port on the remote server that tunnels back to you:

```
$ ssh -R 8000:localhost:80 root@5.161.197.79
```

Requests to port 8000 on the remote server now reach port 80 on your machine (letting `GatewayPorts` clients bind to all interfaces on the server).

**Dynamic forwarding** (`-D`) turns SSH into a SOCKS proxy, useful when your host has no direct Internet but the remote one does:

```
$ ssh -D 1080 192.168.70.2      # apps set to SOCKS localhost:1080 go out via the server
```

**X11 forwarding** (`-X`) tunnels the X protocol so a graphical program on the server draws on your screen (needs `X11Forwarding yes` in `sshd_config`):

```
$ ssh -X 192.168.70.2
$ xeyes                          # window opens locally
```

### GnuPG: creating and sharing keys

**GnuPG** (`gpg`) applies public-key crypto to files and mail. Keys and settings live in `~/.gnupg/`. Generate a key pair:

```
$ gpg --gen-key           # or --full-generate-key for all options
$ gpg --list-keys
```

Export your public key to share it, adding `-a` (armor) for ASCII text, and let others import it:

```
$ gpg --export -a jadi > jadi.pub.key
$ gpg --import jadi.pub.key      # what a recipient runs
```

### Encrypting and decrypting files

Encrypt for a recipient with their public key; only their private key can open it:

```
$ gpg --recipient jadi@example.com --encrypt file.txt    # writes file.txt.gpg
$ gpg --output out.txt --decrypt file.txt.gpg            # needs your private key
```

The file can travel over any channel: everyone can see it, only the holder of the private key can read it.

### Signing and verifying files

Signing is the reverse use of the pair: you apply your **private** key so anyone with your **public** key can confirm the file really came from you and was not changed.

```
$ gpg --output message.sig --sign message.txt   # signed (and compressed) file
$ gpg --verify message.sig                       # check the signature
gpg: Good signature from "Jadi M <jadi@example.com>"
```

Two useful variants: `--clearsign` wraps a readable text message together with its signature in a `.asc` file (so anyone can read it and only the curious verify it), and `--detach-sign` makes a separate `.sig` file that sits beside the untouched original:

```
$ gpg --clearsign message.txt        # message.txt.asc, human-readable + signature
$ gpg --detach-sign report.pdf       # report.pdf.sig, verify against report.pdf
```

### Revocation

If a private key is lost or exposed, a **revocation certificate** tells everyone the key is no longer trustworthy. `gpg --gen-key` already stored one for you; you can also make one explicitly. Publish it (to a keyserver or your site) and others learn the key is dead:

```
$ gpg --output jadi.revoke.asc --gen-revoke jadi@example.com
```

### gpg-agent

Like `ssh-agent`, `gpg-agent` caches your GnuPG passphrase in memory so you are not asked on every single use.

### Summary

Everything here rests on the key pair: a secret private key and a shareable public key, where one encrypts and only the other decrypts. In SSH I trust a server by its host key in `/etc/ssh/ssh_host_*_key`, saved to my `known_hosts`, and I take a sudden change seriously, clearing it with `ssh-keygen -R`. I make my own pair with `ssh-keygen -t` (giving `~/.ssh/id_rsa`/`id_rsa.pub` or `id_ed25519`), enable password-less login by copying the public key into the server's `~/.ssh/authorized_keys` with `ssh-copy-id`, and hold unlocked keys with `ssh-agent`/`ssh-add`. SSH also tunnels: `-L` local, `-R` remote, `-D` a SOCKS proxy, and `-X` for remote graphical apps. GnuPG (`gpg`, from `~/.gnupg/`) does the same for files: I generate and share a key, `--encrypt`/`--decrypt` with a recipient's key, `--sign`/`--verify` (with `--clearsign` and `--detach-sign`) to prove origin and integrity, keep a `--gen-revoke` certificate in case the key is compromised, and let `gpg-agent` cache my passphrase.
