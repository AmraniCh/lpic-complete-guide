# 110.3 Securing data with encryption

**Weight: 4**

The candidate should be able to use public key techniques to secure data and communication.

**Objectives**

- Perform basic OpenSSH 2 client configuration and usage.
- Understand the role of OpenSSH 2 server host keys.
- Perform basic GnuPG configuration, usage and revocation.
- Use GPG to encrypt, decrypt, sign and verify files.
- Understand SSH port tunnels (including X11 tunnels).

**Terms**

`ssh`, `ssh-keygen`, `ssh-agent`, `ssh-add`, `~/.ssh/id_rsa` and `id_rsa.pub`, `~/.ssh/id_ed25519` and `id_ed25519.pub`, `/etc/ssh/ssh_host_rsa_key` and `ssh_host_rsa_key.pub`, `~/.ssh/authorized_keys`, `ssh_known_hosts`, `gpg`, `gpg-agent`, `~/.gnupg/`

### Public key basics

Public key cryptography uses a pair: a **private key** you keep secret, and a **public key** you can share. Anyone can encrypt with the public key, but only the private key can decrypt, and a signature made with the private key can be checked by anyone with the public key. Both SSH and GPG are built on this idea.

### SSH client usage

`ssh` opens an encrypted login to a remote host:

```
$ ssh jadi@server.example.com
$ ssh -p 2222 jadi@server        # non-default port
```

Per user options can go in `~/.ssh/config` so you do not repeat them:

```
# ~/.ssh/config
Host web
    HostName 192.168.1.20
    User jadi
    Port 2222
```

Now `ssh web` is enough.

### Server host keys

Each server has **host keys** in `/etc/ssh/`, such as `ssh_host_ed25519_key` (private) and `ssh_host_ed25519_key.pub` (public). They identify the server. On your first connection you are shown the fingerprint and asked to trust it; the public part is then saved in your `~/.ssh/known_hosts`.

```
The authenticity of host 'server' can't be established.
ED25519 key fingerprint is SHA256:abc123...
Are you sure you want to continue connecting (yes/no)?
```

If a saved host key later changes, SSH refuses to connect and warns loudly, because it could mean someone is impersonating the server. A system wide list of known hosts can also live in `ssh_known_hosts`.

### Key based login

Passwords can be replaced with a key pair, which is both safer and easier to automate. Generate one with `ssh-keygen`:

```
$ ssh-keygen -t ed25519
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/jadi/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
```

This writes the private key `~/.ssh/id_ed25519` and the public key `~/.ssh/id_ed25519.pub` (older setups use `id_rsa`). Copy the public key to the server, where it is appended to `~/.ssh/authorized_keys`:

```
$ ssh-copy-id jadi@server
```

Now the server lets you in if you hold the matching private key. Protect the private key with a passphrase.

### ssh-agent and ssh-add

Typing the passphrase every time is tedious. `ssh-agent` holds unlocked keys in memory for the session, and `ssh-add` loads them:

```
$ eval $(ssh-agent)
$ ssh-add ~/.ssh/id_ed25519
Enter passphrase:
Identity added: /home/jadi/.ssh/id_ed25519
$ ssh-add -l          # list loaded keys
```

After this, connections use the key without asking again until you log out.

### SSH port tunnels

SSH can carry other traffic inside its encrypted connection.

**Local forwarding** (`-L`) makes a local port reach a service through the server:

```
$ ssh -L 8080:localhost:80 jadi@server
```

Now `http://localhost:8080` on your machine reaches port 80 on the server, encrypted the whole way. This secures a service that is otherwise plain text.

**X11 forwarding** (`-X`) tunnels the X protocol so a graphical program on the server draws on your screen:

```
$ ssh -X jadi@server
$ xclock            # window opens locally
```

### GnuPG

**GnuPG** (`gpg`) applies the same public key ideas to files and email. Keys and settings live in `~/.gnupg/`, and `gpg-agent` caches your passphrase much like `ssh-agent`.

Create a key pair:

```
$ gpg --full-generate-key
$ gpg --list-keys
```

Encrypt and decrypt a file for a recipient (using their public key):

```
$ gpg --encrypt --recipient alice@example.com secret.txt   # -> secret.txt.gpg
$ gpg --decrypt secret.txt.gpg > secret.txt                # needs your private key
```

Sign and verify, which proves who created a file and that it was not changed:

```
$ gpg --sign report.pdf              # combined signature
$ gpg --detach-sign report.pdf       # separate report.pdf.sig
$ gpg --verify report.pdf.sig report.pdf
gpg: Good signature from "Jadi <jadi@example.com>"
```

Share your public key so others can verify or encrypt to you:

```
$ gpg --export --armor alice@example.com > alice-pub.asc
$ gpg --import alice-pub.asc
```

### Revocation

If a private key is lost or exposed, a **revocation certificate** tells everyone the key is no longer trustworthy. Generate it in advance and store it safely, because you cannot make one without the private key:

```
$ gpg --gen-revoke alice@example.com > revoke.asc
```

When needed, import it and publish, and the key is marked revoked.

### Summary

I anchor everything on the key pair: a secret private key and a shareable public key. With SSH I log in using `ssh` (with shortcuts in `~/.ssh/config`), and I trust a server by its host key in `/etc/ssh/`, whose public part lands in my `known_hosts`; a sudden change is a warning I take seriously. I prefer key login: `ssh-keygen` makes `id_ed25519` and `id_ed25519.pub`, `ssh-copy-id` appends the public key to the server's `authorized_keys`, and `ssh-agent` with `ssh-add` holds my unlocked key so I am not asked each time. SSH also tunnels traffic, with `-L` to protect a plain service and `-X` for remote graphical apps. GnuPG applies the same ideas to files from `~/.gnupg/`: `gpg` encrypts and decrypts with a recipient's key, and signs and verifies to prove origin and integrity, while a revocation certificate made ahead of time lets me retire a compromised key.
