# 110.1 Perform security administration tasks

**Weight: 3**

Candidates should know how to review system configuration to ensure host security in accordance with local security policies.

**Objectives**

- Audit a system to find files with the suid/sgid bit set.
- Set or change user passwords and password aging information.
- Being able to use nmap and netstat to discover open ports on a system.
- Set up limits on user logins, processes and memory usage.
- Determine which users have logged in to the system or are currently logged in.
- Basic sudo configuration and usage.

**Terms**

`find`, `passwd`, `fuser`, `lsof`, `nmap`, `chage`, `netstat`, `sudo`, `/etc/sudoers`, `su`, `usermod`, `ulimit`, `who`, `w`, `last`

### su versus sudo

`su` substitutes one user identity for another. `su -` becomes root (the `-` loads root's environment), and it asks for the **target** user's password:

```
$ whoami
jadi
$ su -
Password:            # root's password
# whoami
root
```

`sudo` instead runs a single command with root privileges after asking for **your own** password, provided you are allowed to. So `sudo ls` runs `ls` as root. This is safer than `su`: it is per command, logged, and controlled by rules, so you never share the root password. That also explains `sudo su -`: run `su -` as root using your own password.

Who may use `sudo` is set in `/etc/sudoers`:

```
root    ALL=(ALL:ALL) ALL                 # root can run anything, as anyone
%sudo   ALL=(ALL:ALL) ALL                 # the 'sudo' group can too (% = group)
web     ALL=(root) /usr/bin/systemctl     # 'web' may run only this, as root
```

`ALL=(ALL:ALL) ALL` reads as: on all hosts, run as any user and group, all commands. Narrow the last part to grant just one command. Always edit this file with `visudo`, which checks the syntax before saving so a typo cannot lock everyone out.

### Who is logged in

Three commands answer "who is on this machine":

```
$ w            # logged-in users and what each is running, plus load average
$ who          # logged-in users and their login time
$ last         # login history from /var/log/wtmp (most recent first)
```

`w` and `who` show only current sessions (each terminal window is a separate login). `last` also shows people who have logged out. For failed logins, read the bad-login file:

```
$ last -f /var/log/btmp     # failed login attempts; watch for guessing
```

### Passwords and aging

`passwd` changes a password, shows status, and locks accounts:

```
$ passwd              # change my own (asks for the current one)
# passwd jadi         # root sets another user's, no old password needed
$ passwd -S jadi      # status
jadi P 2023-09-14 0 99999 7 -1
# passwd -l jadi      # lock
# passwd -u jadi      # unlock
# passwd -e jadi      # expire now, forcing a change at next login
```

The `-S` line reads: username, `P` (a valid password; `L` locked, `NP` none), last change, then the minimum, maximum, warning, and inactivity days. To change a user's shell or home you use `usermod` (from 107.1); to manage the aging fields you use `chage`:

```
# chage -l jadi       # list current aging
# chage jadi          # interactive, prompts for each field
# chage -M 90 -m 7 -W 3 jadi   # max 90 days, min 7, warn 3 days ahead
```

### suid and sgid files

When the **suid** bit is set on an executable, it runs with the file owner's rights, not the caller's; **sgid** does the same for the group. That is necessary and safe for a few tools, and dangerous elsewhere. `passwd` needs it to edit the shadow file as root even when a normal user runs it:

```
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 63K Nov 23 2022 /usr/bin/passwd
```

The `s` in the owner's execute position is suid. The risk: if an attacker set suid on a copy of `vi` (owned by root), any user could then edit any file as root. So auditing suid and sgid files is a routine security check:

```
# find / -perm -4000 -type f 2>/dev/null    # suid files
/usr/bin/passwd
/usr/bin/sudo
# find / -perm -2000 -type f 2>/dev/null    # sgid files
# find / -perm -u+s 2>/dev/null             # suid, symbolic form
```

An unexpected suid binary, especially a shell or editor, is a red flag.

### User limits

`ulimit` (part of PAM) caps the resources a user's processes may use. Show them, or set one:

```
$ ulimit -a          # all current limits
$ ulimit -u          # max user processes
$ ulimit -t 1        # cap CPU time at 1 second; a longer process is killed
```

A `ulimit` change only affects the current shell. There are **soft** limits (which a user may raise up to the hard cap) and **hard** limits (the real ceiling). Permanent, per-user limits go in `/etc/security/limits.conf`, which protects a machine from a runaway process or a fork bomb:

```
# /etc/security/limits.conf
@students  hard  nproc      20     # the students group: at most 20 processes
*          hard  nofile     8192   # everyone: at most 8192 open files
jadi       -     maxlogins  4       # jadi: at most 4 simultaneous logins
```

### Open ports

An open port is a door into the machine, and malware often opens one, so checking them regularly matters. `netstat` (or the newer `ss`) lists sockets. A memorable switch set is `-tuna` (tcp, udp, numeric, all):

```
$ netstat -tuna
Proto Local Address        Foreign Address      State
tcp   0.0.0.0:80           0.0.0.0:*            LISTEN
tcp   127.0.0.1:3306       0.0.0.0:*            LISTEN
tcp   192.168.1.35:49574   173.194.122.231:443 ESTABLISHED
```

`LISTEN` sockets are servers waiting for connections; `ESTABLISHED` are active connections. `0.0.0.0` means all interfaces, while `127.0.0.1` is local only.

`lsof -i` shows which program owns each connection, and `fuser` finds the process using a specific port:

```
# lsof -i
COMMAND  PID  USER   NODE NAME
nginx  11095  root   TCP *:http (LISTEN)
# fuser 22/tcp -v
                USER  PID ACCESS COMMAND
22/tcp:         root    1 F....  systemd
```

### nmap

Where `netstat` looks from inside, `nmap` scans a host from the network to see which ports answer, so you learn what an outsider can reach:

```
# nmap localhost
PORT     STATE SERVICE
80/tcp   open  http
3306/tcp open  mysql
9050/tcp open  tor-socks
```

By default it scans the common ports and prints the open ones. Comparing `nmap` (outside view) with `netstat`/`ss` (inside view) shows whether a service is exposed more widely than intended. Only scan machines you are allowed to.

### Summary

I review a host along several lines. I prefer `sudo` over `su`, because it grants rights per command, is logged, and is configured in `/etc/sudoers` through `visudo`, whereas `su -` needs the target's password. I see who is on the machine with `w`, `who`, and `last` (and failed logins with `last -f /var/log/btmp`). I set and lock passwords with `passwd` (`-S`, `-l`, `-u`, `-e`), change accounts with `usermod`, and manage aging with `chage -M`/`-m`/`-W`. I hunt dangerous permissions with `find / -perm -4000` and `-2000` (or `-u+s`). I cap resources with `ulimit` now and `/etc/security/limits.conf` permanently, mindful of soft versus hard limits. And I check exposure two ways: `netstat`/`ss` with `lsof` and `fuser` from inside, and `nmap` from the network.
