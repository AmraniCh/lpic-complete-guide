# 106.1 Install and configure X11

**Weight: 2**

Candidates should be able to install and configure X11.

**Objectives**

- Understanding of the X11 architecture.
- Basic understanding and knowledge of the X Window configuration file.
- Overwrite specific aspects of Xorg configuration, such as keyboard layout.
- Understand the components of desktop environments, such as display managers and window managers.
- Manage access to the X server and display applications on remote X servers.
- Awareness of Wayland.

**Terms**

`/etc/X11/xorg.conf`, `/etc/X11/xorg.conf.d/`, `~/.xsession-errors`, `xhost`, `xauth`, `DISPLAY`, `X`

### The X11 architecture

A graphical desktop is built as layers, each doing one job. At the bottom is the hardware (the monitor) and the Linux kernel with its drivers. On top sits a **display server**, the program that accepts drawing requests and turns them into something the kernel and drivers understand. X is one of the two main display servers; the modern one is Wayland.

```
   application (X client)          e.g. xterm, firefox
          |  X protocol (can cross the network)
   display server (X / Xorg)       draws pixels, reads keyboard/mouse
          |
   kernel + drivers
          |
   hardware (monitor, GPU, input)
```

X is **network transparent**: it is a client/server protocol. The confusing part is the naming. The **X server** runs on the machine with the screen, keyboard, and mouse, the machine in front of you. The **X clients** are the applications, and they can run on another machine and still draw on your server. `X11` is version 11 of that protocol, and `Xorg` (from the X.Org Foundation) is the common open-source implementation, the successor to the old XFree86.

Above the display server sit the higher layers you interact with: a **display manager** draws the graphical login screen, a **window manager** draws and moves the window frames, and a **desktop environment** bundles a window manager with panels and applications. Those are covered in 106.2.

### /etc/X11/xorg.conf

This used to be the main configuration file for X. These days Xorg detects the hardware and starts with no config file at all. When you do need one, generate a starting point:

```
$ Xorg -configure        # writes xorg.conf.new, then move it to /etc/X11/xorg.conf
```

The file is a set of sections, each describing one part of the system:

```
Section "InputDevice"
    Identifier  "Generic Keyboard"
    Driver      "kbd"
    Option      "XkbModel"   "pc105"
    Option      "XkbLayout"  "us"
EndSection

Section "Device"            # the graphics card: driver, bus id, options
    Identifier  "Card0"
    Driver      "radeon"
EndSection

Section "Monitor"
    Identifier  "Generic Monitor"
EndSection

Section "Screen"            # ties a Device to a Monitor, sets depth and modes
    Identifier   "Screen0"
    Device       "Card0"
    Monitor      "Generic Monitor"
    DefaultDepth 24
EndSection

Section "ServerLayout"      # glues the screen and input devices together
    Identifier   "DefaultLayout"
    Screen       "Screen0"
    InputDevice  "Generic Keyboard"
EndSection
```

Other sections you may see are `Files` (font paths) and `Module` (features to load, such as `glx` for 3D). A general understanding of these sections is enough; you rarely write one by hand now.

### /etc/X11/xorg.conf.d/ and overriding one aspect

Editing the vendor's `xorg.conf` is risky: a system update could overwrite your changes or lose the vendor's. The modern fix is a drop-in directory. Put your own snippets in `/etc/X11/xorg.conf.d/` as separate `.conf` files and leave `/etc/X11/xorg.conf` untouched. Small files, easy to manage, and updates never fight your edits.

This is how you override just one thing, such as the keyboard layout, without a full config. To set a French layout system-wide:

```
# /etc/X11/xorg.conf.d/00-keyboard.conf
Section "InputClass"
    Identifier  "system-keyboard"
    MatchIsKeyboard "on"
    Option      "XkbLayout" "fr"
EndSection
```

### ~/.xsession-errors

If anything goes wrong while X or your session starts, the errors are written to `~/.xsession-errors`. When a graphical login fails or an app will not start, this is the first file to read.

### xhost

`xhost` controls which machines may talk to your X server, by host. On its own it shows the current access status:

```
$ xhost
access control enabled, only authorized clients can connect
SI:localuser:jadi
```

Open it to everyone, close it again, or allow a single address:

```
$ xhost +                 # anyone can connect (insecure, tests only)
access control disabled, clients can connect from any host
$ xhost -                 # back to authorized clients only
$ xhost +192.168.42.85    # allow just this machine
192.168.42.85 being added to access control list
```

After the last command, the machine `192.168.42.85` may send its graphical requests to this X server.

### DISPLAY

The `DISPLAY` variable tells a graphical program which X server and screen to draw on. Its form is `host:display.screen`:

```
$ echo $DISPLAY
:0
```

An empty host means the local server, and `:0` is the first display. Point it at another machine and the program's window appears there:

```
$ export DISPLAY=192.168.42.80:0
$ xeyes                   # the eyes show up on 192.168.42.80
```

This often will not work as-is, because most distributions do not let X listen for remote connections, for security. The safe way to run a remote graphical program is SSH X11 forwarding, covered in 106.2.

### xauth

Where `xhost` grants access by host, `xauth` grants it by a shared secret. X writes a token into `~/.Xauthority`, and any client that knows the token may connect to the server. It is per user rather than per machine, so it is safer than opening a host. If X misbehaves, one troubleshooting step is to delete `~/.Xauthority` and restart X.

### Wayland

X11 is very old and only keeps working through many patches, so one of its own developers started a modern replacement called **Wayland**. In Wayland the compositor handles both drawing and window management, which is simpler and more secure. Many distributions now default to Wayland and keep X11 as a fallback. For LPIC-1 you only need to be aware that it exists and is steadily replacing X.

### Summary

I think of X as layers: hardware, kernel and drivers, then a display server, then the applications. X is a network-transparent client/server protocol, where the `X` server is the machine with my screen and the clients are the apps, which is why an app on another host can draw on my display; `X11` is the protocol version and `Xorg` the implementation. Xorg mostly configures itself, but a full config lives in `/etc/X11/xorg.conf` as sections (InputDevice, Device, Monitor, Screen, ServerLayout), and I can generate one with `Xorg -configure`. To change one thing, such as the keyboard `XkbLayout`, I drop a small file into `/etc/X11/xorg.conf.d/` and leave the vendor file alone. When a session breaks I read `~/.xsession-errors`. For remote display I control access with `xhost` (by host) or `xauth` (by secret), point `DISPLAY` at a server, and know the display manager, window manager, and desktop environment are the layers above. Finally, I am aware that Wayland is the modern, more secure replacement for X.
