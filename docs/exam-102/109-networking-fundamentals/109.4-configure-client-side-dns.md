# 109.4 Configure client side DNS

**Weight: 2**

Candidates should be able to configure DNS on a client host.

**Objectives**

- Query remote DNS servers.
- Configure local name resolution and use remote DNS servers.
- Modify the order in which name resolution is done.
- Debug errors related to name resolution.
- Awareness of systemd-resolved

**Terms**

`/etc/hosts`, `/etc/resolv.conf`, `/etc/nsswitch.conf`, `host`, `dig`, `getent`

### How a name becomes an address

When a program looks up a name, the C library follows the `hosts:` line in `/etc/nsswitch.conf`, which usually says check the local file first, then DNS:

```
hosts:  files dns
```

- `files` reads `/etc/hosts`.
- `dns` asks the servers listed in `/etc/resolv.conf`.

```
   getaddrinfo("db.local")
          |
   /etc/nsswitch.conf : hosts: files dns
          |                     |
   /etc/hosts  --miss-->  /etc/resolv.conf --> DNS server
```

### /etc/hosts

A static local list, checked before DNS when the order is `files dns`:

```
127.0.0.1      localhost
192.168.1.20   db.local db
```

This is the fastest way to name a machine without a DNS server, and it overrides DNS for those names.

### /etc/resolv.conf

Lists the DNS servers and the search domain:

```
nameserver 192.168.1.1
nameserver 8.8.8.8
search example.com
```

`nameserver` lines are tried in order. `search example.com` lets you type `web` and have it tried as `web.example.com`. On modern systems this file is often generated, so set servers through NetworkManager or systemd-resolved rather than editing it directly.

### Changing the resolution order

To make DNS win over `/etc/hosts`, swap the `hosts:` line in `/etc/nsswitch.conf`:

```
hosts:  dns files
```

Now names are resolved by DNS first and only fall back to the local file.

### Querying DNS

`host` gives a short answer, good for a quick check:

```
$ host www.example.com
www.example.com has address 93.184.216.34
```

`dig` gives full detail, good for debugging. You can also ask a specific server or a specific record type:

```
$ dig example.com MX
;; ANSWER SECTION:
example.com.  3600  IN  MX  10 mail.example.com.
$ dig @8.8.8.8 example.com    # ask a specific server
```

Note that `host` and `dig` talk to DNS directly, so they ignore `/etc/hosts`. To test the full path the way an application sees it, including `/etc/hosts` and nsswitch order, use `getent`:

```
$ getent hosts db.local
192.168.1.20   db.local
```

### Debugging name resolution

A useful sequence:

- `getent hosts name`: does the whole system resolve it (files plus DNS)?
- `host name` or `dig name`: does DNS alone resolve it?
- If `dig @server name` works but plain `dig` does not, the server in `/etc/resolv.conf` is wrong.
- If `getent` finds it but `dig` does not, the answer is coming from `/etc/hosts`.

### Awareness of systemd-resolved

**systemd-resolved** is a local resolver service. When it runs, `/etc/resolv.conf` often points at `127.0.0.53`, and you query and inspect it with `resolvectl`. For LPIC-1 you only need to know it exists and why the loopback nameserver appears.

### Summary

I trace a lookup through `/etc/nsswitch.conf`, whose `hosts:` line sets the order, normally `files dns`: first `/etc/hosts`, then the servers in `/etc/resolv.conf`. I add quick local names in `/etc/hosts`, set DNS servers and a `search` domain in `/etc/resolv.conf`, and I can flip the order to `dns files` when I want DNS to win. For queries I use `host` for a short answer and `dig` for detail, including `dig @server` and record types like `MX`, remembering that both bypass `/etc/hosts`, so `getent hosts` is what shows me the real system view. To debug I compare `getent`, `host`/`dig`, and `dig @server`, which isolates whether the fault is the server, the local file, or DNS itself. I also recognize systemd-resolved by the `127.0.0.53` nameserver it installs.
