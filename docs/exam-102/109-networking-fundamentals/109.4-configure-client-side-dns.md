# 109.4 Configure client side DNS

**Weight: 2**

Candidates should be able to configure DNS on a client host.

**Objectives**

- Query remote DNS servers.
- Configure local name resolution and use remote DNS servers.
- Modify the order in which name resolution is done.
- Debug errors related to name resolution.
- Awareness of systemd-resolved

**Terms**

`/etc/hosts`, `/etc/resolv.conf`, `/etc/nsswitch.conf`, `host`, `dig`, `getent`

### DNS and the resolver

The **Domain Name System (DNS)** translates names such as `x.org` into IP addresses. A client needs to know which DNS server to ask, and that is set in `/etc/resolv.conf`:

```
$ cat /etc/resolv.conf
# Generated by NetworkManager
nameserver 192.168.1.1
nameserver 4.2.2.4
search jadi.net
```

`nameserver` lines are the servers to query, in order; `search` lets a short name like `tv` be tried as `tv.jadi.net`. On modern systems a manager (NetworkManager or systemd-resolved) generates this file, so you usually set the servers in the manager rather than editing it by hand.

### host

`host` is the simple lookup tool. With no options it returns every record it finds:

```
$ host kernel.org
kernel.org has address 139.178.84.217
kernel.org has IPv6 address 2604:1380:4641:c500::1
kernel.org mail is handled by 10 smtp1.kernel.org.
```

That is an A (IPv4), an AAAA (IPv6), and MX (mail) records. Ask for one type with `-t`:

```
$ host -t A kernel.org      # only the IPv4 address
$ host -t MX kernel.org     # only the mail servers
```

### dig

`dig` is the detailed DNS query tool. It shows the answer plus which server replied and the TTL:

```
$ dig x.org
;; QUESTION SECTION:
;x.org.            IN   A
;; ANSWER SECTION:
x.org.      1625   IN   A   131.252.210.176
;; Query time: 35 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)
```

The `1625` is the **TTL**, how many seconds the answer may be cached. The `SERVER` line tells you which resolver answered, useful when debugging. To query a specific server instead of the configured one, use `@`:

```
$ dig @8.8.8.8 google.com
;; ANSWER SECTION:
google.com.   112  IN  A  173.194.32.133
google.com.   112  IN  A  173.194.32.136
...
;; SERVER: 8.8.8.8#53(8.8.8.8)
```

Asking `8.8.8.8` directly is how you tell whether the problem is your configured resolver or the name itself: if `dig @8.8.8.8 name` works but a plain `dig name` does not, your `/etc/resolv.conf` is at fault.

### /etc/hosts

`/etc/hosts` is static, local name resolution: a table of addresses and names, editable by root, that can answer without any DNS server:

```
127.0.0.1       localhost
192.168.59.231  mass1
172.16.12.134   linuxclass wonderland
```

Because it is normally consulted before DNS, an entry here wins over the real DNS answer. `ping mass1` reaches `192.168.59.231` even though DNS returns NXDOMAIN for that name, and adding `127.0.0.1 facebook.com` would send your browser to your own machine for that site. This is handy for LAN names and testing, and something to check when a name resolves "wrongly".

### /etc/nsswitch.conf: the resolution order

`/etc/nsswitch.conf` sets which sources answer each kind of lookup, and in what order. The `hosts:` line controls name resolution:

```
hosts:  files mdns4_minimal [NOTFOUND=return] dns myhostname
```

Read left to right: `files` checks `/etc/hosts` first, then `dns` asks the servers in `/etc/resolv.conf`. Put `dns` before `files` and DNS is tried first. `[NOTFOUND=return]` stops the search if a source authoritatively says the name does not exist. Changing this line is how you "modify the order in which name resolution is done".

### getent

`getent` reads the databases through nsswitch, so it resolves a name exactly the way real programs do (honouring both `/etc/hosts` and DNS), unlike `dig` and `host` which talk only to DNS. That makes it the right tool to confirm what the system actually resolves:

```
$ getent hosts mass1
192.168.59.231  mass1
$ getent hosts kernel.org
139.178.84.217  kernel.org
```

### Awareness: systemd-resolved

`systemd-resolved` is systemd's resolver service. It listens for DNS queries on `127.0.0.53` and answers after consulting its own configuration, and it is what generates `/etc/resolv.conf` on many systems (often as a symlink). `resolvectl status` shows its current servers. For LPIC-1 you only need to be aware it exists.

### Summary

A client resolves names using the servers in `/etc/resolv.conf` (`nameserver` and `search`), though a manager usually generates that file. I query DNS directly with `host` (simple, `-t` for one record type) and `dig` (detailed, showing TTL and the answering `SERVER`, and `@server` to pick a resolver), and `dig @8.8.8.8` versus a plain `dig` tells me whether my resolver or the name is the problem. `/etc/hosts` gives static local names checked before DNS, so an entry there overrides the real answer, and `/etc/nsswitch.conf`'s `hosts:` line sets the order (`files dns`), which is how I change resolution priority. To see what the system truly resolves, honouring both files and DNS, I use `getent hosts`. And I am aware that `systemd-resolved` is the systemd resolver listening on `127.0.0.53`.
