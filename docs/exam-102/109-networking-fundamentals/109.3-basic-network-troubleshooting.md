# 109.3 Basic network troubleshooting

**Weight: 4**

Candidates should be able to troubleshoot networking issues on client hosts.

**Objectives**

- Manually configure network interfaces, including viewing and changing the configuration of network interfaces using iproute2.
- Manually configure routing, including viewing and changing routing tables and setting the default route using iproute2.
- Debug problems associated with the network configuration.
- Awareness of legacy net-tools commands.

**Terms**

`ip`, `hostname`, `ss`, `ping`, `ping6`, `traceroute`, `traceroute6`, `tracepath`, `tracepath6`, `netcat`, `ifconfig`, `netstat`, `route`

### A method for troubleshooting

When someone says "I cannot open web pages", work outward step by step: does the interface have an IP and is it up, is the routing right (can you reach the gateway and the Internet), and does DNS work. Each step rules out a layer. The modern tools are the **iproute2** suite (`ip`, `ss`); the older **net-tools** (`ifconfig`, `netstat`, `route`) do the same jobs and are worth recognising.

`hostname` confirms which machine you are on, an easy first sanity check:

```
$ hostname
debian
```

### Checking the interface: ip and ifconfig

An interface needs a correct address and netmask. `ip addr show` (or the older `ifconfig`) shows them:

```
$ ip addr show
2: enp0s25: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
    link/ether 8c:a9:82:7b:89:06 brd ff:ff:ff:ff:ff:ff
    inet 192.168.1.35/24 brd 192.168.1.255 scope global enp0s25
```

Here the address `192.168.1.35/24` looks fine. If an interface has no `inet` line, or is `state DOWN`, that is the problem. (`man ip-address` gives help on a specific `ip` subcommand.)

### ping and ping6

`ping` sends ICMP packets and reports the replies. It is the fastest way to test reachability. Work up from near to far. First the default gateway, which you should always be able to reach:

```
$ ip route show
default via 192.168.70.1 dev enp0s1
$ ping 192.168.70.1
64 bytes from 192.168.70.1: icmp_seq=1 ttl=64 time=1.11 ms
```

Then a known Internet address by IP (`4.2.2.4` is a popular test), then a name:

```
$ ping 4.2.2.4          # works: routing to the Internet is fine
$ ping google.com
ping: unknown host google.com
```

Reaching `4.2.2.4` but not `google.com` (with "unknown host") points straight at **DNS**: the machine cannot turn the name into an address. Check `/etc/resolv.conf` for a valid `nameserver`. Use `ping6` for IPv6 targets. (Note that a "paranoid" network may block ICMP, so a failed ping is not always a real outage.)

### Routing problems

A different symptom: you can ping the gateway but the Internet is "Network is unreachable". That is a **missing default route**, the machine does not know where to send packets outside its own subnet. View and fix the routing table with `ip route` (or the legacy `route`, or `netstat -nr`):

```
$ ping 8.8.8.8
connect: Network is unreachable
$ ip route show
192.168.70.0/24 dev enp0s1 proto kernel scope link src 192.168.70.2
# ip route add default via 192.168.70.1     # add the missing gateway
$ ping 8.8.8.8
64 bytes from 8.8.8.8: icmp_seq=1 ttl=55 time=316 ms
```

Changes made with `ip route` are temporary and lost at reboot; make them permanent in the config files. `netstat -nr` shows the same table in the old format:

```
$ netstat -nr
Destination     Gateway         Genmask         Flags Iface
0.0.0.0         192.168.70.1    0.0.0.0         UG    enp0s1
192.168.70.0    0.0.0.0         255.255.255.0   U     enp0s1
```

### traceroute and tracepath

When a route works but is slow or fails partway, `traceroute` shows each hop between you and the target, so you can see where it breaks:

```
$ traceroute 4.2.2.4
 1  192.168.70.1        0.619 ms        # my router
 2  10.192.0.1          421.898 ms      # my ISP
 4  * * *                               # this hop blocks ICMP
11  d.resolvers.level3.net (4.2.2.4)  601 ms   # destination
```

`* * *` means that hop is not replying (often ICMP is blocked there). `tracepath` is essentially the same tool for LPIC purposes, and `traceroute6`/`tracepath6` are the IPv6 versions.

### ss and netstat

`ss` (iproute2) and the older `netstat` show sockets and connections. The most useful combination is `ss -tulpn`: **t**cp, **u**dp, **l**istening, **p**rocess, **n**umeric. It answers "what is listening on this machine, and which program owns it":

```
$ ss -tulpn
Netid State  Local Address:Port   Process
tcp   LISTEN 127.0.0.1:631        (cupsd)
tcp   LISTEN 0.0.0.0:22           (sshd)
tcp   LISTEN 0.0.0.0:25           (master)
```

That tells you whether a service is actually up and on which address (only `127.0.0.1`, or all interfaces `0.0.0.0`).

### netcat

`nc` (netcat) is a swiss-army knife for TCP, UDP, and Unix sockets: opening connections, listening on a port, or a quick port test, over IPv4 or IPv6. Unlike `telnet` it scripts cleanly. Listen on one terminal, connect from another:

```
$ nc -l 1337                 # listen on port 1337
$ nc localhost 1337          # connect and type; text appears on the listener
Are you enjoying the LPIC?
```

This is a fast way to check whether a port is open and passing traffic.

### dig

For a quick DNS check, `dig` looks up a name and shows which server answered:

```
$ dig google.com
;; ANSWER SECTION:
google.com.   293  IN  A  216.58.214.46
;; SERVER: 4.2.2.4#53(4.2.2.4)
```

If `ping name` fails but `dig name` (or `dig @8.8.8.8 name`) returns an address, the resolver config is the fault, not the network.

### Summary

I troubleshoot outward. First `hostname` and `ip addr show` confirm the interface has an address and is up (the legacy `ifconfig` does the same). Then `ping` the gateway, then an Internet IP like `4.2.2.4`, then a name: reaching the IP but not the name means DNS, so I check `/etc/resolv.conf`; "Network is unreachable" means a missing default route, which I view and fix with `ip route show`/`add default` (temporary until saved), or see with `route`/`netstat -nr`. `traceroute` (and `tracepath`, plus the `6` IPv6 variants) shows where along the path traffic dies, with `* * *` for hops blocking ICMP. `ss -tulpn` (or `netstat`) lists what is listening and which process owns it, and `nc` tests whether a port passes traffic. Throughout I know the iproute2 tools `ip` and `ss` are the modern replacements for the net-tools `ifconfig`, `route`, and `netstat`.
