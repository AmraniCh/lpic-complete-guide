# 109.3 Basic network troubleshooting

Candidates should be able to troubleshoot networking issues on client hosts.

**Objectives**

- Manually configure network interfaces, including viewing and changing the configuration of network interfaces using iproute2.
- Manually configure routing, including viewing and changing routing tables and setting the default route using iproute2.
- Debug problems associated with the network configuration.
- Awareness of legacy net-tools commands.

**Terms**

`ip`, `hostname`, `ss`, `ping`, `ping6`, `traceroute`, `traceroute6`, `tracepath`, `tracepath6`, `netcat`, `ifconfig`, `netstat`, `route`

### iproute2: the ip command

`ip` is the modern tool for interfaces, addresses and routes. It replaces the older `ifconfig` and `route`. These changes are runtime only and are lost at reboot, which is exactly what you want while testing.

```
$ ip addr show           # or: ip a
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
    inet 192.168.1.20/24 brd 192.168.1.255 scope global eth0
$ ip link show           # interfaces and their up/down state
$ ip -s link show eth0   # with packet and error counters
```

Bring an interface up or down, and add or remove an address:

```
$ ip link set eth0 up
$ ip link set eth0 down
$ ip addr add 192.168.1.30/24 dev eth0
$ ip addr del 192.168.1.30/24 dev eth0
```

### Routing with ip route

The routing table decides where a packet goes. The **default route** (the gateway) is used for any address not on a local subnet.

```
$ ip route show
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.20
$ ip route add default via 192.168.1.1     # set the gateway
$ ip route add 10.0.0.0/8 via 192.168.1.254  # a route to another network
$ ip route del 10.0.0.0/8
```

No default route is a classic fault: local machines work but nothing on the internet does.

### Testing reachability

`ping` sends ICMP echo requests. It answers the first question of any network problem: can I reach the other host at all?

```
$ ping -c3 192.168.1.1
64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=0.35 ms
--- 192.168.1.1 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss
```

`ping6` is the IPv6 version. Ping the gateway first, then an outside address like `8.8.8.8`, then a name like `google.com`. Where it first fails tells you the layer: local link, routing, or DNS.

### Tracing the path

`traceroute` and `tracepath` show each router (hop) a packet passes through, useful when a distant host is unreachable but the gateway is fine:

```
$ tracepath example.com
 1:  192.168.1.1          0.4ms
 2:  10.20.30.1           8.1ms
 3:  no reply
```

The hop where replies stop is roughly where the trouble is. `traceroute6` and `tracepath6` are the IPv6 versions.

### Sockets and ports: ss

`ss` shows sockets: which ports are listening and which connections are open. It replaces the older `netstat`.

```
$ ss -tlnp
State   Recv-Q  Local Address:Port   Process
LISTEN  0       0.0.0.0:22           users:(("sshd",pid=712))
LISTEN  0       127.0.0.1:631        users:(("cupsd",pid=690))
```

The flags: `-t` TCP, `-u` UDP, `-l` listening, `-n` numeric (no name lookup), `-p` process. This answers "is my service actually listening, and on which address".

### netcat

`netcat` (`nc`) opens raw TCP or UDP connections, handy to test whether a remote port is open:

```
$ nc -zv 192.168.1.10 22
Connection to 192.168.1.10 22 port [tcp/ssh] succeeded!
```

### Legacy net-tools

The older `net-tools` package is still found on many systems. Know the mapping:

| Legacy | Modern |
|---|---|
| `ifconfig` | `ip addr`, `ip link` |
| `route` | `ip route` |
| `netstat` | `ss` |

```
$ ifconfig eth0
$ route -n
$ netstat -tlnp
```

### Summary

I troubleshoot from the inside out with iproute2. `ip addr` and `ip link` show and change interfaces, `ip route` shows and sets routes including the all important default gateway, and these edits are runtime only, perfect for testing. To find where a problem lives I `ping` the gateway, then an outside IP, then a name; the first step that fails points at link, routing or DNS. `traceroute`/`tracepath` show which hop is stuck for distant hosts. `ss -tlnp` tells me which services are listening on which ports, and `netcat` tests whether a remote port answers. I also remember the legacy `net-tools` equivalents, `ifconfig`, `route` and `netstat`, since I still meet them on older systems.
