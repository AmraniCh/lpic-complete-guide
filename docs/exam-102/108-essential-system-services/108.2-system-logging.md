# 108.2 System logging

**Weight: 4**

Candidates should be able to configure rsyslog. This objective also includes configuring the logging daemon to send log output to a central log server or accept log output as a central log server. Use of the systemd journal subsystem is covered. Also, awareness of syslog and syslog-ng as alternative logging systems is included.

**Objectives**

- Basic configuration of rsyslog.
- Understanding of standard facilities, priorities and actions.
- Query the systemd journal.
- Filter systemd journal data by criteria such as date, service or priority.
- Configure persistent systemd journal storage and journal size.
- Delete old systemd journal data.
- Retrieve systemd journal data from a rescue system or file system copy.
- Understand interaction of rsyslog with systemd-journald.
- Configuration of logrotate.
- Awareness of syslog and syslog-ng.

**Terms**

`/etc/rsyslog.conf`, `/var/log/`, `logger`, `logrotate`, `/etc/logrotate.conf`, `/etc/logrotate.d/`, `journalctl`, `systemd-cat`, `/etc/systemd/journald.conf`, `/var/log/journal/`

### How logging works

The kernel, services, and programs all generate logs, and examining them is how you understand a running system. If every program managed its own logs the formats and locations would be chaos, so Unix uses a central logging service instead.

The older tool was `syslog`, then `syslog-ng` (new generation), then **rsyslog**, which most distributions used for years and which is still common. rsyslog receives messages from many programs (even over the network), writes them as **text** files you can read with `grep`, `less`, `tail`, or `zless`, and can trigger actions. These days **systemd** brings its own logger, `journald`, read with `journalctl`; its logs are **binary**, not text.

Under the hood, whatever wants to log sends its message to the `/dev/log` or `/dev/kmsg` devices, and the logging daemon reads from there and processes it.

### dmesg and the kernel ring buffer

Some messages happen before the disks are ready, for example early in boot. The kernel stores these in the **kernel ring buffer**, which you read with `dmesg`:

```
$ dmesg | tail
[    3.221093] usb 1-1: new high-speed USB device number 2
[    5.882014] EXT4-fs (sda1): mounted filesystem with ordered data mode
```

### Log rotation with logrotate

Logs grow, and something must trim them so the disk does not fill. `logrotate` does this. Its main config is `/etc/logrotate.conf`, and packages add their own rules in `/etc/logrotate.d/`:

```
# /etc/logrotate.conf
weekly            # rotate logs weekly
rotate 4          # keep 4 old copies, delete older
create            # create a new empty log after rotating
#compress         # gzip the rotated files
include /etc/logrotate.d
```

```
# /etc/logrotate.d/apt
/var/log/apt/term.log {
  rotate 12
  monthly
  compress
  missingok      # no error if the log is absent
  notifempty     # skip rotation if the log is empty
}
```

Common directives are `weekly`/`monthly`, `rotate N` (how many to keep), `compress`, `missingok`, `create MODE OWNER GROUP`, and `prerotate`/`postrotate` scripts. `logrotate` itself is run daily by `/etc/cron.daily/logrotate`.

### Log files in /var/log

Logs live under `/var/log/`. When something breaks, `ls -ltrh /var/log/` to spot recently touched files is a good first move. Some important ones (Debian names):

| File | Holds |
|---|---|
| `/var/log/auth.log` | authentication: logins, `sudo`, cron auth |
| `/var/log/syslog` | catch-all for messages with no specific file |
| `/var/log/kern.log` | kernel messages |
| `/var/log/messages` | informational service messages, default for remote clients |
| `/var/log/wtmp`, `/var/run/utmp` | successful logins (read with `last`, `who`) |
| `/var/log/btmp` | failed logins (read with `lastb`) |
| `/var/log/lastlog` | time of each user's most recent login |

Services also make their own subdirectories, such as `/var/log/apache2/` or `/var/log/mysql/`.

### rsyslog

rsyslog's config is `/etc/rsyslog.conf`, plus anything in `/etc/rsyslog.d/`. It has three sections:

- **MODULES**: input/output modules to load, for example `imudp` to receive syslog over UDP.
- **GLOBAL DIRECTIVES**: general settings such as file ownership and the include of `/etc/rsyslog.d/`.
- **RULES**: the heart of it, lines of `facility.priority   action`.

```
# RULES
auth,authpriv.*     /var/log/auth.log
cron.*              -/var/log/cron.log
kern.*              -/var/log/kern.log
mail.*              -/var/log/mail.log
*.emerg             :omusrmsg:*
```

A rule is **facility**, a dot, **priority**, then an **action**.

The **facility** says where the message came from: `kern`, `user`, `mail`, `daemon`, `cron`, `auth`, `authpriv`, `syslog`, `security`, and others.

The **priority** says how important it is. In increasing order:

```
debug  info  notice  warning  err  crit  alert  emerg
```

Selecting a priority also selects everything more important. So `cron.notice` logs notice and up (warning, err, crit, alert, emerg). To match one priority *exactly*, put `=` in front: `local3.=alert /var/log/alert.log`.

The **action** is usually a file, but can be a logged-in user to notify on screen, or `@ip` to forward to a remote log server:

```
kern.panic   @192.168.1.100     # send kernel panics to a central log server
*.*          /var/log/messages  # everything, every level, to one file
```

That is how you build a central log server (it receives with the `imudp`/`imtcp` modules) or a client that ships logs to one. Note that kernel logging is handled by a separate daemon, `klogd`, so kernel crashes can still be recorded even after the rest has fallen over.

### logger

`logger` sends a message into the logging system from the command line or a script, handy for testing rules:

```
# logger Testing my tool
# logger -p local1.emerg "Nothing emergency for sure"
# tail -1 /var/log/syslog
2023-06-30T06:13:27 debian root: Testing my tool
```

### The systemd journal: journald

On systemd, `systemd-journald` collects everything (service output, kernel messages, anything sent to the journal) into **binary** files, read with `journalctl`. Its config is `/etc/systemd/journald.conf`. rsyslog and journald coexist: journald can forward to rsyslog (the `ForwardToSyslog=yes` option), so you often have both the binary journal and the text files in `/var/log/`.

### Querying the journal

Plain `journalctl` shows everything, which is too much. The useful switches:

| Switch | Meaning |
|---|---|
| `-r` | reverse, newest first |
| `-f` | follow (live tail) |
| `-e` | jump to the end |
| `-n N` | last N lines |
| `-k` | kernel messages only (like `dmesg`) |
| `-b` | this boot; `-b -1` the previous one (`--list-boots` to list) |
| `-p` | a priority and up, e.g. `-p err` |
| `-u` | one systemd unit, e.g. `-u ssh` |

Add `--since` and `--until` for a time range, either as `YYYY-MM-DD HH:MM:SS` or friendly forms like `--since "10 minutes ago"`, `--since yesterday`:

```
$ journalctl -u ssh -p err --since "1 hour ago"
$ journalctl -b -n 50
```

### systemd-cat

`systemd-cat` sends output into the journal manually, either from a pipe or by running a command:

```
# echo "This is my first test" | systemd-cat
# systemd-cat -p info uptime      # run uptime, log its output at info priority
```

### Journal storage and cleanup

By default the journal is persistent only if `/var/log/journal/` exists; otherwise it lives in memory under `/run/log/journal/` and is lost on reboot. Control this in `/etc/systemd/journald.conf`:

```
Storage=persistent   # always keep on disk (creates /var/log/journal/)
Storage=volatile     # memory only
Storage=auto         # disk only if /var/log/journal/ exists (default)
Storage=none         # keep nothing
```

Disk use is capped with `SystemMaxUse` (default 10%), `SystemKeepFree` (default 15%), `SystemMaxFileSize`, and `SystemMaxFiles` (in-memory equivalents are the `Runtime*` versions). To delete old data by hand:

```
# journalctl --vacuum-time=3months    # drop entries older than 3 months
# journalctl --vacuum-size=1G          # shrink the journal to 1G
# journalctl --vacuum-files=5          # keep only 5 archive files
```

### Reading logs from a broken system

Because the journal is just files under `/var/log/journal/<machine-id>/`, you can read the logs of a machine that will not boot. Mount its disk elsewhere and point `journalctl` at the files:

```
$ journalctl -D /mnt/var/log/journal/ec22e43962c64359b9b25cfa650b025b/
$ journalctl --root /mnt      # let journalctl find the journal under /mnt
```

`--merge` folds them into your own view, and `--file` reads a single journal file.

### Summary

Linux logs centrally. Historically that was `syslog`, then `syslog-ng`, then `rsyslog`, which writes text files to `/var/log/`; systemd adds `journald`, whose binary logs I read with `journalctl`, and the two interoperate through `ForwardToSyslog`. Early kernel messages sit in the ring buffer, read with `dmesg`. I keep files from growing with `logrotate` (`/etc/logrotate.conf` and `/etc/logrotate.d/`, run daily by cron). rsyslog's rules are `facility.priority action`: the priority selects that level and everything more severe (or exactly one with `=`), and the action is a file, a user, or `@ip` to a central server, which is how I build or feed a log server. I inject test messages with `logger` and `systemd-cat`. For the journal I query with `journalctl` (`-u`, `-p`, `-b`, `-k`, `--since`), make it persistent with `Storage=persistent` in `/etc/systemd/journald.conf`, cap and vacuum it with `SystemMaxUse` and `--vacuum-*`, and read a dead machine's logs with `journalctl -D` or `--root`.
