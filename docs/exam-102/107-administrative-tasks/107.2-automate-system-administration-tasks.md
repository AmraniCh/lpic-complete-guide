# 107.2 Automate system administration tasks by scheduling jobs

**Weight: 4**

Candidates should be able to use cron and systemd timers to run jobs at regular intervals and to use at to run jobs at a specific time.

**Objectives**

- Manage cron and at jobs.
- Configure user access to cron and at services.
- Understand systemd timer units.

**Terms**

`/etc/cron.{d,daily,hourly,monthly,weekly}/`, `/etc/at.deny`, `/etc/at.allow`, `/etc/crontab`, `/etc/cron.allow`, `/etc/cron.deny`, `/var/spool/cron/`, `crontab`, `at`, `atq`, `atrm`, `systemctl`, `systemd-run`

Sometimes a command must run at set times or intervals: a backup every morning at 03:00, or a web index refreshed every hour. The common tools are `crontab` for repeating intervals, `at` for a single future time, and the timers built into systemd.

### Crontab format

A crontab line has six fields. The first five say *when*, and everything after them is the command.

```
A  B  C  D  E  command and arguments
```

| Field | Meaning | Values |
|---|---|---|
| A | minute | 0-59 |
| B | hour | 0-23 |
| C | day of month | 1-31 |
| D | month | 1-12 (or names) |
| E | day of week | 0-7 (0 and 7 are Sunday, or names) |

A `*` means "any". A `/` slices a range (`*/5` in the minute field is every five minutes), and a `,` lists values (`8,18` means 8 and 18). There are also shortcuts like `@reboot` and `@daily` that replace the five time fields.

```
5 0 * * *        $HOME/bin/daily.job      # 00:05 every day
15 14 1 * *      $HOME/bin/monthly        # 14:15 on the 1st of each month
0 22 * * 1-5     echo "it is 10pm"        # 22:00 on weekdays (Mon-Fri)
23 0-23/2 * * *  echo "23 min past every 2nd hour"
*/5 * * * *      echo "every 5 minutes"
42 8,18 * * 1-5  echo "08:42 and 18:42 on weekdays"
@reboot          echo "runs once after each reboot"
```

A line like `42 8 1 1 0` runs only when the 1st of January is a Sunday. When a cron job produces output, cron e-mails it to the job's owner.

### User crons

Cron is a service. Each user has their own crontab, managed with:

```
$ crontab -l        # list my cron jobs
$ crontab -e        # edit them (validated, then loaded)
$ crontab -r        # remove my crontab
```

These are stored under `/var/spool/cron/` (for example `/var/spool/cron/crontabs/jadi` or `/var/spool/cron/tabs/jadi`). Never edit those files directly; always use `crontab -e`, which validates and installs the new version.

### System-wide cron: /etc/crontab

`/etc/crontab` looks like a user crontab but adds one field, the **user** the command runs as, and it is edited directly with an editor:

```
A  B  C  D  E  USER  command and arguments
```

```
# cat /etc/crontab
SHELL=/bin/sh
PATH=/usr/bin:/usr/sbin:/sbin:/bin
MAILTO=root

17 *    * * *   root    cd / && run-parts --report /etc/cron.hourly
```

The first lines set the shell, the search path, and who receives the output e-mail. This system crontab is what runs the interval directories described next.

### /etc/cron.d and the hourly/daily/weekly/monthly directories

`/etc/cron.d/` holds extra system crontab files (same format as `/etc/crontab`, with a user field), one per package:

```
$ cat /etc/cron.d/munin
MAILTO=root
*/5 * * * *  munin  if [ -x /usr/bin/munin-cron ]; then /usr/bin/munin-cron; fi
```

More convenient are the interval directories. Any script dropped into `/etc/cron.hourly/`, `/etc/cron.daily/`, `/etc/cron.weekly/`, or `/etc/cron.monthly/` runs at that interval, no crontab line needed. This keeps routine cleanup and backup scripts tidy:

```
$ ls /etc/cron.daily
apt  dpkg  logrotate  man-db  mlocate  passwd
```

To schedule a daily job, you just copy your executable script into `/etc/cron.daily/`.

### at: run once at a future time

Where cron repeats, `at` runs something a single time. Type the commands, then end with Ctrl+D (shown as `<EOT>`):

```
$ at now + 1 min
warning: commands will be executed using /bin/sh
at> touch /tmp/at
at> <EOT>
job 3 at Thu Oct 29 22:12:00 2015
```

`at` understands friendly times such as `teatime` (16:00), `tomorrow`, `17:30`, and `noon`. `atq` lists the queue and `atrm` deletes a job by number:

```
$ atq
5    Fri Oct 30 22:15:00 2015 a jadi
4    Fri Oct 30 16:00:00 2015 a jadi
$ atrm 4
```

### Controlling access to cron and at

Four files decide who may use these services:

```
/etc/cron.allow   /etc/cron.deny
/etc/at.allow     /etc/at.deny
```

Usually none exist. If you create them they behave as:

| File | Effect |
|---|---|
| `.allow` | only the users listed may use the service, everyone else is denied |
| `.deny` | everyone may use it except the users listed |

### systemd timers and systemd-run

Most distributions now ship systemd, which can schedule jobs with **timer units** instead of cron. A timer file ends in `.timer` and activates a matching `.service` of the same name.

A **real-time** timer fires on a calendar expression with `OnCalendar=`, close to cron. The `*`, `/`, and `,` work as in cron, and systemd adds `..` for a range:

```
# /etc/systemd/system/myservice.timer
[Unit]
Description=Run my service

[Timer]
OnCalendar=Sat *-*-1..7 02:42:00    # 02:42 on the first Saturday each month
Persistent=true

[Install]
WantedBy=timers.target
```

There are word shortcuts too: `OnCalendar=daily`, `hourly`, `weekly`, `monthly`, `yearly`.

A **monotonic** timer fires a set time after an event, using one of `OnActiveSec`, `OnBootSec`, `OnStartupSec`, `OnUnitActiveSec`, or `OnUnitInactiveSec`:

```
[Timer]
OnUnitActiveSec=5minutes 20seconds   # 5m20s after the unit was last activated
```

After adding a timer, reload and enable it, and list the active ones with `systemctl`:

```
# systemctl daemon-reload
# systemctl enable --now myservice.timer
# systemctl list-timers          # add --all to include inactive ones
```

For a quick one-off without writing unit files, `systemd-run` starts a transient unit:

```
# systemd-run --on-active="2hours" /usr/local/bin/helloworld.sh
```

Timer output goes to the journal, so read it with `journalctl` (add `--user` for user-level timers).

### Summary

I pick the tool by the need. For repeating jobs I use cron: a line of five time fields (minute, hour, day-of-month, month, day-of-week) plus a command, with `*`, `/`, and `,`, edited per user through `crontab -e` and stored under `/var/spool/cron/`. System jobs live in `/etc/crontab` and `/etc/cron.d/` (both add a user field), and dropping a script into `/etc/cron.hourly`, `.daily`, `.weekly`, or `.monthly` schedules it with no crontab line. For a single future run I use `at` (with `atq` to list and `atrm` to remove), and cron output is e-mailed to the owner. Access is gated by `/etc/cron.allow` and `/etc/cron.deny` (and the `at` equivalents), where an `.allow` file is a whitelist and a `.deny` file a blacklist. On systemd I use `.timer` units with `OnCalendar=` or a monotonic `OnBootSec=`-style option, enable them with `systemctl`, and fire a quick one with `systemd-run`.
