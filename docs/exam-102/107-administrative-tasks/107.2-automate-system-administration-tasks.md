# 107.2 Automate system administration tasks by scheduling jobs

Candidates should be able to use cron and systemd timers to run jobs at regular intervals and to use at to run jobs at a specific time.

**Objectives**

- Manage cron and at jobs.
- Configure user access to cron and at services.
- Understand systemd timer units.

**Terms**

`/etc/cron.{d,daily,hourly,monthly,weekly}/`, `/etc/at.deny`, `/etc/at.allow`, `/etc/crontab`, `/etc/cron.allow`, `/etc/cron.deny`, `/var/spool/cron/`, `crontab`, `at`, `atq`, `atrm`, `systemctl`, `systemd-run`

### cron for repeating jobs

`cron` runs jobs on a schedule. Each user has a personal crontab, edited with `crontab -e` and stored under `/var/spool/cron/`. Never edit that spool file by hand.

```
$ crontab -e     # edit my crontab
$ crontab -l     # list my crontab
$ crontab -r     # remove my crontab
```

A crontab line has five time fields then the command:

```
 .---------------- minute (0 - 59)
 |  .------------- hour (0 - 23)
 |  |  .---------- day of month (1 - 31)
 |  |  |  .------- month (1 - 12)
 |  |  |  |  .---- day of week (0 - 6, Sunday = 0)
 |  |  |  |  |
 *  *  *  *  *   command to run
```

Examples:

```
30 2 * * *      /usr/local/bin/backup.sh      # every day at 02:30
0  */4 * * *    /usr/local/bin/sync.sh         # every 4 hours
0  9  * * 1-5   /usr/local/bin/report.sh       # weekdays at 09:00
*/15 * * * *    /usr/local/bin/check.sh        # every 15 minutes
```

A `*` means every value, `*/n` means every n steps, `a-b` a range, and `a,b,c` a list.

### System crontabs

`/etc/crontab` and the files in `/etc/cron.d/` are system wide. They add a sixth field, the **user** to run as, before the command:

```
# /etc/crontab
17 3 * * * root /usr/local/bin/rotate-logs.sh
```

For jobs that only need to run at a rough frequency, drop an executable script into one of these directories and cron runs it for you:

```
/etc/cron.hourly/    /etc/cron.daily/
/etc/cron.weekly/    /etc/cron.monthly/
```

### Controlling who may use cron

Access is decided by two files:

- If `/etc/cron.allow` exists, only users listed in it may use cron.
- Otherwise, if `/etc/cron.deny` exists, everyone except those listed may use cron.
- If neither exists, the distribution decides (often only `root`).

`at` uses the same rule with `/etc/at.allow` and `/etc/at.deny`.

### at for a one-time job

`at` runs a command once, at a time you name. The job is read from standard input, ending with Ctrl-D.

```
$ at 22:00
warning: commands will be executed using /bin/sh
at> /usr/local/bin/backup.sh
at> <EOT>
job 3 at Mon Sep  7 22:00:00 2026
```

Time can be written many ways: `at now + 1 hour`, `at 9am tomorrow`, `at midnight`.

```
$ atq                 # list pending jobs
3   Mon Sep  7 22:00:00 2026 a jadi
$ atrm 3              # remove job 3
```

### systemd timers

systemd offers timers as an alternative to cron. A timer needs two unit files with the same name: a `.service` that does the work and a `.timer` that says when.

```
# /etc/systemd/system/backup.service
[Service]
ExecStart=/usr/local/bin/backup.sh
```

```
# /etc/systemd/system/backup.timer
[Timer]
OnCalendar=*-*-* 02:30:00
Persistent=true

[Install]
WantedBy=timers.target
```

Enable and start the timer, then check it:

```
$ systemctl enable --now backup.timer
$ systemctl list-timers
```

`OnCalendar` gives an absolute schedule, while `OnBootSec` or `OnUnitActiveSec` schedule relative to boot or the last run. `Persistent=true` runs a missed job once the machine is back on, which plain cron does not do.

For a quick one-off without writing files, `systemd-run` schedules a transient job:

```
$ systemd-run --on-active=30min /usr/local/bin/cleanup.sh
```

### Summary

For anything that repeats I reach for `cron`: my own jobs go in `crontab -e` (stored in `/var/spool/cron/`), and the five fields are minute, hour, day of month, month and day of week. System jobs live in `/etc/crontab` and `/etc/cron.d/` and add a user field, while dropping a script into `/etc/cron.daily/` and friends handles rough schedules. I gate access with `cron.allow` and `cron.deny` (and the matching `at.allow` and `at.deny`). For a single job at a set time I use `at`, listing with `atq` and cancelling with `atrm`. When I want systemd's features I write a `.service` plus a `.timer` with an `OnCalendar` line and `Persistent=true` so missed runs catch up, enable it with `systemctl enable --now`, and check `systemctl list-timers`; for a throwaway job `systemd-run --on-active` does it without files.
