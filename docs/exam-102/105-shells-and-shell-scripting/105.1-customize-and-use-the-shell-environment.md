# 105.1 Customize and use the shell environment

Candidates should be able to customize shell environments to meet users' needs. Candidates should be able to modify global and user profiles.

**Objectives**

- Set environment variables (e.g. PATH) at login or when spawning a new shell.
- Write Bash functions for frequently used sequences of commands.
- Maintain skeleton directories for new user accounts.
- Set command search path with the proper directory.

**Terms**

`.`, `source`, `/etc/bash.bashrc`, `/etc/profile`, `env`, `export`, `set`, `unset`, `~/.bash_profile`, `~/.bash_login`, `~/.profile`, `~/.bashrc`, `~/.bash_logout`, `function`, `alias`

### Login shells and non-login shells

Which files Bash reads depends on how it starts.

A **login shell** is what you get when you log in on a text console, over SSH, or with `su -`. A **non-login interactive shell** is what you get when you open a new terminal window inside a running session.

```
login shell                 non-login interactive shell
-----------                 ---------------------------
/etc/profile                /etc/bash.bashrc   (Debian)
  -> /etc/profile.d/*.sh    ~/.bashrc
  -> /etc/bash.bashrc
first found of:
  ~/.bash_profile
  ~/.bash_login
  ~/.profile
```

On logout, a login shell reads `~/.bash_logout`.

Because a login shell does not read `~/.bashrc` by default, most `~/.bash_profile` files source it themselves so both kinds of shell share the same settings:

```bash
# ~/.bash_profile
if [ -f ~/.bashrc ]; then
    . ~/.bashrc
fi
```

Global files (`/etc/profile`, `/etc/bash.bashrc`) apply to every user. Per-user files in the home directory apply to one person, and override the global ones because they are read last.

### Environment variables and shell variables

A **shell variable** lives only in the current shell. An **environment variable** is copied into every child process. `export` turns the first into the second.

```
$ greeting="hello"        # shell variable, this shell only
$ export greeting         # now exported to child processes
$ export TZ="Europe/Paris"  # set and export in one step
```

`set` lists all shell variables and functions. `env` lists only exported variables, and can run a command with a changed environment:

```
$ env | grep ^HOME
HOME=/home/jadi
$ env LANG=C sort file.txt   # run sort with LANG=C, just this once
```

`unset` removes a variable:

```
$ unset greeting
```

A quick way to see one value is `echo`:

```
$ echo $HOME
/home/jadi
```

### The PATH

`PATH` is a colon separated list of directories the shell searches for commands. Order matters: the first match wins.

```
$ echo $PATH
/usr/local/bin:/usr/bin:/bin:/usr/local/sbin:/usr/sbin
```

To add your own `bin` directory for the current session, and keep the old value:

```
$ export PATH="$HOME/bin:$PATH"
```

Putting `$HOME/bin` first means your own scripts are found before system commands of the same name. To make the change permanent, put that line in `~/.bashrc` or `~/.bash_profile`.

Real world use: if `which myscript` finds nothing even though the file exists, its directory is almost always missing from `PATH`.

### Aliases

An `alias` is a short name for a longer command. It is expanded only at the start of a command line.

```
$ alias ll='ls -l --color=auto'
$ alias rm='rm -i'     # ask before deleting
$ alias                # list all aliases
alias ll='ls -l --color=auto'
alias rm='rm -i'
```

Remove one with `unalias ll`. Aliases are not passed to scripts or child shells, so for anything reused put it in `~/.bashrc`.

### Functions

A **function** groups commands under a name and can take arguments (`$1`, `$2`, and so on). Use one when an alias is not enough.

```bash
# make a directory and enter it
mkcd () {
    mkdir -p "$1" && cd "$1"
}
```

```
$ mkcd projects/website
$ pwd
/home/jadi/projects/website
```

`declare -f` shows a function's definition, and `unset -f mkcd` removes it. Put functions you reuse in `~/.bashrc`.

### source and the dot command

`source file` (or its short form `. file`) runs a file in the **current** shell, so any variables, aliases or functions it defines stay after it finishes. Running the file normally would use a child shell and lose them.

```
$ source ~/.bashrc     # apply edits without logging out
$ . ~/.bashrc          # same thing
```

This is how you reload your configuration after changing it.

### Skeleton directory for new users

When `useradd -m` creates a home directory, it copies the contents of `/etc/skel/` into it. That is how every new user starts with the same `~/.bashrc`, `~/.profile` and so on.

```
$ ls -A /etc/skel
.bash_logout  .bashrc  .profile
```

To give every future user a default alias or setting, edit the files in `/etc/skel/` before the accounts are created. Existing users are not affected.

### Summary

I think of this objective as two questions: which file do I edit, and does my change survive a new shell. A login shell reads `/etc/profile` and then one of `~/.bash_profile`, `~/.bash_login` or `~/.profile`, while a new terminal reads `/etc/bash.bashrc` and `~/.bashrc`, so I keep reusable settings in `~/.bashrc` and let `~/.bash_profile` source it. I set values with a plain assignment, share them with children using `export`, list them with `set` and `env`, and remove them with `unset`. I extend `PATH` by prepending my own directory so my commands win. For shortcuts I use an `alias`, and for anything with arguments a `function`, both kept in `~/.bashrc`. After editing I run `source ~/.bashrc` so the change applies now instead of after a fresh login. Finally, `/etc/skel/` is the template copied into every new home directory, so that is where I set defaults for future accounts.
