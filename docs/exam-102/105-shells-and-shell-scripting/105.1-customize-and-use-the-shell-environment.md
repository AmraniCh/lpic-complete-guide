# 105.1 Customize and use the shell environment

**Weight: 4**

Candidates should be able to customize shell environments to meet users' needs. Candidates should be able to modify global and user profiles.

**Objectives**

- Set environment variables (e.g. PATH) at login or when spawning a new shell.
- Write Bash functions for frequently used sequences of commands.
- Maintain skeleton directories for new user accounts.
- Set command search path with the proper directory.

**Terms**

`.`, `source`, `/etc/bash.bashrc`, `/etc/profile`, `env`, `export`, `set`, `unset`, `~/.bash_profile`, `~/.bash_login`, `~/.profile`, `~/.bashrc`, `~/.bash_logout`, `function`, `alias`

### Environment variables

Environment variables are special variables that hold configuration the shell uses: what to show in the prompt, where to look for commands, which language to use, and so on. Every distribution ships with some, and you can add, change, or remove your own.

You can list them with `env` or `printenv`, and list everything (including shell-only variables and functions) with `set`.

#### env

`env` prints the environment, runs a command with a changed environment, or starts a command with an empty one.

```
$ env | head -4
SHELL=/bin/bash
HOME=/home/jadi
PATH=/usr/local/bin:/usr/bin:/bin
LANG=en_US.UTF-8
```

Run one command with a variable changed, without touching your shell:

```
$ env LANG=C sort names.txt      # sort using the C locale, just this once
$ env -u LANG mycommand          # run mycommand with LANG removed
$ env -i bash                    # start bash with an empty environment
```

`printenv` is a simpler way to print one variable or all of them:

```
$ printenv HOME
/home/jadi
```

#### set

`set` with no arguments lists every shell variable and function. With options it changes how Bash itself behaves. Turn an option on with `-` and off with `+`.

| Switch | Effect |
|---|---|
| `-b` | report a finished background job immediately, not at the next prompt |
| `-e` | stop the script as soon as any command returns non-zero |
| `-n` | read commands but do not run them, a syntax check for scripts |
| `-t` | exit after reading and running one command |
| `-C` | stop `>` from overwriting an existing file |

`set -e` at the top of a script is common: it makes the script stop at the first failing command instead of carrying on blindly.

#### Setting environment variables

A variable name uses letters, digits, and the underscore, cannot start with a digit, and is traditionally UPPERCASE. Assign with `=` and no spaces around it:

```
$ name=jadi
$ desc='A programmer who enjoys cycling'
$ echo $name
jadi
$ echo $desc
A programmer who enjoys cycling
```

Three rules: no spaces around `=`; quote a value that contains spaces; use `$` only when reading a variable, never when setting it.

The command search path, `PATH`, is one of these variables. It is a colon separated list of directories the shell searches, in order, and the first match wins. Add your own directory:

```
$ echo $PATH
/usr/local/bin:/usr/bin:/bin
$ export PATH="$HOME/bin:$PATH"
```

Putting `$HOME/bin` first means your own command is found before a system command of the same name. Set it in `~/.bashrc` to make it permanent.

#### unset

`unset` removes a variable or a function:

```
$ name=jadi
$ echo $name
jadi
$ unset name
$ echo $name

```

#### export

A plain `name=value` lives only in the current shell, so a command you run (which starts in a sub-shell) will not see it. `export` makes the variable available to the current shell and every sub-shell under it:

```
$ export name=jadi
$ echo $name
jadi
$ bash            # start a sub-shell
$ echo $name
jadi              # still there, because it was exported
```

#### . and source

`source file` (short form `. file`) runs the file in the current shell instead of a child, so any variables, aliases, and functions it defines survive after it finishes. Running the file the normal way starts a child shell and loses them. That is why you reload edited config with `source ~/.bashrc`, and why you see the dot form inside files like `/etc/profile`.

```
$ source ~/.bashrc     # apply your edits now, no need to log out
$ . ~/.bashrc          # exactly the same thing
```

### Aliases

An `alias` is a short name for a longer command, usually kept in `~/.bashrc`:

```
alias ll='ls -alF'
alias la='ls -A'
alias testnet='ping 4.2.2.4'
```

Type `alias` to list them all, and `unalias ll` to remove one. An alias only expands at the start of a command line.

### Functions

A `function` groups commands under a name. Reach for one when a task is too big for an alias or needs arguments (`$1`, `$2`, and so on):

```
funnyls () {
    ls -ltrh
    echo "This is a funny ls"
}
```

Keep functions you reuse in `~/.bashrc` so every new shell has them.

### Different shell environments

Bash can start in three ways, and each reads a different set of files:

- **Login shell**: you enter a username and password, for example a text console login, an SSH session, or `su -`.
- **Interactive non-login shell**: you open a new terminal inside a session that is already running.
- **Non-interactive shell**: a shell that spawns to run a command or a script.

#### Login shell

The files run in this order:

```
1. /etc/profile
     -> runs everything in /etc/profile.d/
2. the FIRST one that exists of:
     ~/.bash_profile     (found? stop here)
     ~/.bash_login       (else, found? stop here)
     ~/.profile          (else)
3. ~/.bashrc
```

Only one of the three user profiles runs: Bash tries `~/.bash_profile`, then `~/.bash_login`, then `~/.profile`, and stops at the first it finds. Personal settings usually go in `~/.bashrc`, and the profile sources it.

#### Interactive non-login shell

Only two files handle the environment:

- `/etc/bash.bashrc` (called `/etc/bashrc` on some systems)
- `~/.bashrc`

#### Non-interactive shell

There is no fixed file. Bash looks at the `BASH_ENV` variable, and if it points to a file, runs it. On most distributions this variable is unset by default.

### A few more files

#### /etc/skel

`/etc/skel` is a template directory. Its contents are copied into a new user's home directory when the account is created (for example `useradd -m`). Edit the files here to give every future user the same starting `~/.bashrc`, `~/.profile`, and so on. Existing users are not affected.

```
$ ls -A /etc/skel
.bash_logout  .bashrc  .profile
```

#### ~/.bash_logout

This runs when you leave a login shell. On many distributions it just clears the screen, so the next person at the console cannot see what you were doing.

### Summary

I treat this objective as knowing which file to edit and how a value spreads. Environment variables hold the shell's configuration; I list them with `env` or `printenv`, list everything with `set`, and I know `set -e` makes a script stop on the first error. I create a variable with `name=value` (no spaces around `=`, quotes for spaces), extend the search path by prepending my directory to `PATH`, remove a variable with `unset`, and share it with sub-shells using `export`. `source` (or `.`) runs a file in the current shell so its settings stick, which is how I reload `~/.bashrc`. For shortcuts I use an `alias`, and for anything with arguments a `function`, both kept in `~/.bashrc`. A login shell reads `/etc/profile`, then `/etc/profile.d/`, then the first of `~/.bash_profile`, `~/.bash_login`, or `~/.profile`, then `~/.bashrc`; a non-login terminal reads `/etc/bash.bashrc` and `~/.bashrc`; a non-interactive shell uses `BASH_ENV` if it is set. Finally, `/etc/skel` is the template copied into every new home directory, and `~/.bash_logout` runs on the way out of a login shell.
