# 105.2 Customize or write simple scripts

Candidates should be able to customize existing scripts, or write simple new Bash scripts.

**Objectives**

- Use standard sh syntax (loops, tests).
- Use command substitution.
- Test return values for success or failure or other information provided by a command.
- Execute chained commands.
- Perform conditional mailing to the superuser.
- Correctly select the script interpreter through the shebang (#!) line.
- Manage the location, ownership, execution and suid-rights of scripts.

**Terms**

`for`, `while`, `test`, `if`, `read`, `seq`, `exec`, `||`, `&&`

### The shebang and running a script

The first line of a script names the interpreter. It starts with `#!` (the shebang) followed by the full path.

```bash
#!/bin/bash
echo "Hello, $USER"
```

A file is not runnable just because it exists. Give it the execute bit, then run it by path:

```
$ chmod +x hello.sh
$ ./hello.sh
Hello, jadi
```

The `./` matters: without it the shell searches `PATH` and will not find a script in the current directory. To run it inside the current shell instead of a child, use `source hello.sh`.

### Variables, arguments and command substitution

Scripts read positional arguments as `$1`, `$2` and so on. `$0` is the script name, `$#` is the argument count, and `$@` is all arguments.

**Command substitution** captures the output of a command into a variable with `$( )`:

```bash
#!/bin/bash
today=$(date +%F)
count=$(ls | wc -l)
echo "On $today this directory holds $count entries"
```

`read` pauses and stores what the user types:

```bash
read -p "Your name: " name
echo "Welcome, $name"
```

### Return values

Every command sets an exit status in `$?`: `0` means success, anything else means failure.

```
$ ls /etc/passwd
/etc/passwd
$ echo $?
0
$ ls /nope
ls: cannot access '/nope': No such file or directory
$ echo $?
2
```

Testing `$?` is how a script knows whether the previous step worked.

### Chaining commands

You can join commands by their exit status:

- `A && B` runs `B` only if `A` succeeded.
- `A || B` runs `B` only if `A` failed.
- `A ; B` runs `B` regardless.

```
$ mkdir build && cd build          # enter only if mkdir worked
$ ping -c1 host || echo "host down"  # message only if ping failed
```

### Tests

`test` (also written as `[ ]`) checks a condition and sets the exit status. Common checks:

| Test | True when |
|---|---|
| `-f file` | file exists and is a regular file |
| `-d dir` | directory exists |
| `-z "$s"` | string is empty |
| `-n "$s"` | string is not empty |
| `"$a" = "$b"` | strings are equal |
| `"$x" -eq "$y"` | numbers are equal |
| `"$x" -gt "$y"` | x is greater than y |

```
$ [ -f /etc/passwd ] && echo "it is there"
it is there
```

Always quote variables inside `[ ]`. An unquoted empty variable breaks the test.

### if

`if` runs a block when a test succeeds:

```bash
#!/bin/bash
if [ -f "$1" ]; then
    echo "$1 is a file"
elif [ -d "$1" ]; then
    echo "$1 is a directory"
else
    echo "$1 is neither"
fi
```

### Loops

`for` walks a list. `seq` generates a range of numbers to walk.

```bash
for user in alice bob carol; do
    echo "Making home for $user"
done

for n in $(seq 1 5); do
    echo "backup part $n"
done
```

`while` repeats as long as a test stays true. This pattern reads a file line by line:

```bash
while read line; do
    echo "got: $line"
done < input.txt
```

### Conditional mail to the superuser

A cron script that finds a problem can warn `root` by piping a message to `mail`. Sending it only on failure keeps the mailbox quiet the rest of the time.

```bash
#!/bin/bash
if ! df -h | grep -q '/backup'; then
    echo "Backup disk is not mounted" | mail -s "Backup alert" root
fi
```

### exec

`exec` replaces the current shell with another command instead of starting a child. Nothing after it runs, because the original process is gone.

```bash
exec >> /var/log/myscript.log 2>&1   # redirect all later output to a log
```

Used at the top of a script, this sends everything the script prints to a log file.

### Location and permissions of scripts

Personal scripts belong in `~/bin`, system wide ones in `/usr/local/bin`, both usually on `PATH`. A script should be owned correctly and be executable:

```
$ ls -l /usr/local/bin/backup.sh
-rwxr-xr-x 1 root root 412 Sep  6 10:20 /usr/local/bin/backup.sh
```

Avoid the **suid** bit on shell scripts. It asks the kernel to run the script as its owner (often `root`), and shell scripts are easy to trick, so most systems ignore suid on them anyway. When a task truly needs extra rights, use `sudo` with a narrow rule instead.

### Summary

When I write a script I start with a shebang like `#!/bin/bash`, make it executable with `chmod +x`, and run it as `./script`. Inside, I read arguments as `$1` and friends, capture output with `$(command)`, and prompt with `read`. I lean on the exit status in `$?`, chaining steps with `&&` and `||` so later commands depend on earlier ones. For decisions I use `test` (the `[ ]` form) inside `if`, always quoting my variables, and for repetition I use `for` with `seq` or `while` reading a file. A common admin trick is to pipe a message to `mail root` only when something failed, so cron stays quiet otherwise. I keep scripts in `~/bin` or `/usr/local/bin`, owned sensibly and executable, and I avoid the suid bit on them, reaching for `sudo` when a job really needs more rights.
