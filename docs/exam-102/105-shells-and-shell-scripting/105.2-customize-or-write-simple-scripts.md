# 105.2 Customize or write simple scripts

**Weight: 4**

Candidates should be able to customize existing scripts, or write simple new Bash scripts.

**Objectives**

- Use standard sh syntax (loops, tests).
- Use command substitution.
- Test return values for success or failure or other information provided by a command.
- Execute chained commands.
- Perform conditional mailing to the superuser.
- Correctly select the script interpreter through the shebang (#!) line.
- Manage the location, ownership, execution and suid-rights of scripts.

**Terms**

`for`, `while`, `test`, `if`, `read`, `seq`, `exec`, `||`, `&&`

### Combining commands

To run several commands on one line, separate them with `;`. So `cd /tmp; ls` runs `cd /tmp` and then `ls`, no matter what.

Two smarter joins depend on whether the previous command succeeded:

- `A && B` (logical AND) runs `B` only if `A` succeeded.
- `A || B` (logical OR) runs `B` only if `A` failed.

The shell stops as soon as the result is decided. In `A && B`, if `A` fails the whole thing is already false, so `B` is skipped. In `A || B || C`, if `A` succeeds the result is already true, so `B` and `C` are skipped; each next command runs only because the previous one failed.

This is how you build safe flows:

```
$ cp backup.gz /backups/ && rm backup.gz    # delete the file ONLY if the copy worked
$ ping -c1 host || echo "host is down"      # message ONLY if the ping failed
```

### Shell scripts

A shell script is a file of commands, plus some logic and loops, run as one larger command. Scripts are how you automate a task: a `do_backup.sh` might compress some files, rename the archive with the current date, copy it to a remote host, and delete archives older than a month.

### The shebang

The first line of a script starts with `#!` followed by the interpreter that should run it. It is called the **shebang**, and it tells the shell which program to hand the script to.

```bash
#!/bin/bash

echo
echo "We are learning! Wowww..."
echo
```

Common shebangs are `#!/bin/bash` and `#!/bin/sh`. `sh` is a more basic shell but compatible with most of this. Do not confuse the shebang with a comment: a plain `#` at the start of a line is a comment, `#!` on the very first line is the shebang.

### Variables and arguments

You define variables as `NAME=VALUE`, and quote the value if it contains spaces:

```bash
#!/bin/bash
NAME="Jadi the geeking guy"
echo "$NAME is learning! Wowww..."
```

A script reads its command-line arguments as `$1`, `$2`, and so on, and `$#` holds how many arguments were given:

```bash
#!/bin/bash
echo "first argument: $1"
echo "there are $# arguments"
```

### Command substitution

To capture the output of a command into a variable, or drop it into another command, use `$(command)` (or the older backtick form `` `command` ``):

```
$ FILES=$(ls -1)                          # $FILES now holds the file list
$ date +'%Y%m%d-%H%M'
20230408-1604
$ touch backup_$(date +'%Y%m%d-%H%M').tar
$ ls
backup_20230408-1604.tar
```

### Executing a script

In Linux a file has to be marked executable before you can run it. Add the execute bit with `chmod +x`, then run the script by giving its path. The shell does not search the current directory, so a script in the current directory must be run as `./script.sh`:

```
$ chmod +x myscript.sh
$ ./myscript.sh
```

You can also run it by passing it to an interpreter: `sh myscript.sh` or `bash myscript.sh`.

All of those run the script in a child process that returns to your shell when it finishes. `exec` is different: it **replaces** the current shell with the program, so nothing after the `exec` runs. The `-c` switch runs the command in a clean, empty environment.

```
$ exec ./longtask.sh          # this shell becomes longtask.sh; it does not come back
```

Inside a script, `exec` is often used to send all later output to a log file:

```bash
exec >> /var/log/myscript.log 2>&1
```

### Location, ownership and suid of scripts

Keep personal scripts in `~/bin` and system-wide ones in `/usr/local/bin`, both of which are normally on `PATH`. A script should be owned sensibly and be executable:

```
$ ls -l /usr/local/bin/backup.sh
-rwxr-xr-x 1 root root 412 Sep  6 10:20 /usr/local/bin/backup.sh
```

Avoid the **suid** bit on shell scripts. It asks the kernel to run the script as its owner (often `root`), but shell scripts are easy to trick, so most systems ignore suid on them anyway. When a job genuinely needs extra rights, give it a narrow `sudo` rule instead.

### Conditions

To add logic you need conditions, tested with `if`:

```bash
if [ condition ]
then
   do something
else
   do another thing
fi
```

The `else` part is optional; `if`, `then`, `fi` is enough. The command that actually checks a condition is `test`, but because it is used so often there is a shortcut: instead of `test condition` you write `[ condition ]`. Mind the spaces inside the brackets and around `=`.

```bash
#!/bin/bash
kernel=$(uname -s)
if [ "$kernel" = "Linux" ]
then
    echo "YES. You are using Linux"
else
    echo "Not a Linux :("
fi
```

Common tests:

| Test | True when |
|---|---|
| `"a" = "b"` | the two strings are equal |
| `"a" != "b"` | the strings are not equal |
| `4 -lt 40` | first number is lower than the second |
| `5 -gt 15` | first number is greater than the second |
| `5 -ge 5` | greater than or equal |
| `5 -le 3` | lower than or equal |
| `9 -ne 2` | the numbers are not equal |
| `-f FILE` | FILE exists |
| `-s FILE` | FILE exists and is larger than zero bytes |
| `-x FILE` | FILE exists and is executable |

### read

`read` takes input from the user into a variable:

```bash
#!/bin/sh
echo "what is your name?"
read NAME
echo "Hello $NAME"
```

`-p` shows a prompt, and `-t` gives it a timeout in seconds so the script does not wait forever:

```bash
if read -t 10 -p "Server address? " SERVER
then
    echo "Connecting to $SERVER ..."
else
    echo
    echo "Too late!"
fi
```

### Loops

Bash has two loops. `for` repeats a set number of times, once per item in a list. `while` repeats as long as a condition stays true.

`for` walks a list of numbers, files, or words:

```bash
for NUM in 1 2 3 4 5 6
do
    echo $NUM
done
```

For a longer range use `seq`, or the shorthand `{1..42}`: `seq 1 42` and `{1..42}` both count one to forty-two. The list can be command output too:

```bash
for FILE in $(ls)
do
    echo $FILE
    wc -l $FILE
done
```

`while` keeps going until its condition is false. If the condition never becomes false you get an infinite loop, stopped with Ctrl+C:

```bash
VAR=52
while [ $VAR -gt 42 ]
do
    echo "VAR is $VAR and it is still greater than 42"
    let VAR=VAR-1
done
```

Note `let`: it does arithmetic. Without it, `VAR=$VAR+1` would just glue the text together into `1+1` rather than add.

### Mailing the root user

A script can warn the administrator by e-mailing `root`. You need an MTA or `mailutils` installed, then `mail` sends the message. Interactively:

```
$ mail root
Cc:
Subject: Hi there root
hello there. This is my mail
```

From inside a script, pipe the body in and set the subject with `-s`. Sending it only when something is wrong keeps the mailbox quiet the rest of the time:

```bash
if ! df -h | grep -q '/backup'
then
    echo "Backup disk is not mounted" | mail -s "Backup alert" root
fi
```

### Return values

Every program returns a value when it finishes. By convention `0` means success and anything else means a specific failure. The shell keeps the last one in `$?`:

```
$ touch /chert
touch: cannot touch '/chert': Permission denied
$ echo $?
1
$ touch /tmp/11
$ echo $?
0
$ test -e /
$ echo $?
0
$ test -e /nonexist
$ echo $?
1
$ dummycommand
dummycommand: command not found
$ echo $?
127
```

Testing `$?` is how a script knows whether the previous step worked. To set the return value of your own script, use `exit`, for example `exit 0` for success.

### Summary

I build a script from the pieces in order. I chain commands with `;`, `&&`, and `||` so a step runs only when the previous one succeeded or failed. Every script starts with a shebang like `#!/bin/bash`, and I make it executable with `chmod +x` and run it as `./script`, keeping personal ones in `~/bin` and shared ones in `/usr/local/bin`, and avoiding the suid bit in favour of a narrow `sudo` rule. Inside, I read arguments as `$1` and `$#`, and capture output with `$(command)`. For logic I use `if` with `test` (the `[ ]` form), remembering the spaces, and I know the string, numeric, and file tests. `read` (with `-p` and `-t`) takes user input, `for` with `seq` or `{1..42}` repeats over a list, and `while` with `let` repeats on a condition. A common admin trick is to pipe a message to `mail root` only on failure. Finally, I check the exit status in `$?` (0 for success) and set my own script's status with `exit`.
